# PWA Style Guide (INFRA-1593)

Single source of truth for the visual + component vocabulary of the operator
PWA (`web/v2/`). Before inventing a new CSS variable, breakpoint, or
component slot, check here first. This doc exists because `welcome.js` and
`cockpit.js` each invented their own tokens with nothing canonical to point
them at — don't repeat that.

**Ownership:** authored once (this PR), then amended by the `tech-writer`
agent (`docs/agents/tech-writer.md`, hourly) as new components ship. See
[Maintenance](#maintenance) at the bottom.

## 1. Design tokens

Source of truth: `web/v2/index.html` `:root` (dark, default) plus
`[data-theme="light"]` and `[data-theme="high-contrast"]` overrides.

|---|---|---|---|---|

| `--bg-surface` | `#141414` | `#ffffff` | `#000000` | Card / panel background |
| `--bg-elevated` | `#1e1e1e` | `#f0f0f0` | `#1a1a1a` | Modals, popovers, elevated surfaces |

| `--radius-sm` | `6px` | (same) | (same) | Small corner radius (buttons, pills) |
| `--nav-width` | `64px` | (same) | (same) | Sidebar cadence rail width |

Theme is selected via `data-theme` attribute on `<html>` (`light` /
`high-contrast`; omitted = dark default). Every new component must consume
these variables via `var(--token)` — never redeclare a color literal. Full
enforcement rules: [`docs/process/CSS_TOKEN_DISCIPLINE.md`](../process/CSS_TOKEN_DISCIPLINE.md)
(§6 below).

## 3. Composition rules

Where does a new component go? Decision tree:

1. **Is it always-visible across every cadence** (NOW/AMBIENT/LIBRARY/CONFIG)? → **App header** (`#app-header`), next to `<chump-nav>`. Examples: `<chump-heartbeat>`, `<chump-model-indicator>`, `<chump-autopilot-toggle>`.
2. **Is it a persistent status strip pinned to the bottom of the viewport?** → **Footer** (`<chump-status-footer>`'s slot). Reserve for one line of glanceable state — do not stack multiple footer components.
3. **Is it the primary content for one cadence or sub-tab?** → **View chrome** — a `<chump-view-*>` element rendered into `#main-content`, routed by `chump-nav`'s cadence/sub-tab selection. This is the default answer for new features.
4. **Does it need to interrupt the operator regardless of current view** (a blocking confirmation, a kill-switch notice, an approval request)? → **Floating overlay** — `role="dialog"` or `role="alertdialog"`, `aria-modal="true"`, rendered above everything via a fixed-position container (see `.qa-overlay`, `.ootb-root` for precedent). Must support Escape-to-close (§5, anti-patterns §8).
5. **Is it a self-contained widget nested inside an existing view** (e.g. a panel inside the cockpit cadence)? → **Cadence sub-component** — imported and composed by the parent `<chump-view-*>`, not registered as a separate nav destination.

If none of these fit cleanly, it's a signal the feature needs its own
cadence or sub-tab — raise that as a design question before building, not
after.

## 4. Mobile breakpoints

Central breakpoint set. `640px` is the dominant mobile cap used throughout
`web/v2/index.html`'s `@media` rules (12+ occurrences) — treat it as
canonical; don't invent a sibling value without updating this table.

| Breakpoint | Device class | What changes and why |
|---|---|---|
| `375px` | iPhone narrow (SE-class) | Floor for touch-target and text-wrap testing. No dedicated media query today — content must not clip or overflow below this width. |
| `640px` | Mobile cap (canonical `max-width: 640px`) | `chump-nav` collapses from a left-side vertical rail to a horizontal top strip; cadence buttons become `flex: 1` with a max-width of 80px; sub-tabs move below the cadence strip. Most single-column reflows happen at this breakpoint. |
| `768px` | Tablet | Two-column layouts (where present) collapse to one column; side panels that float on desktop become full-width sheets. |
| `1024px` | Laptop narrow | Sidebar/rail widths may shrink; secondary metadata columns (timestamps, secondary actions) may hide in favor of primary content. |
| `1440px` | Laptop wide | Max-width content containers apply — do not let text lines or cards stretch edge-to-edge on wide viewports. |

When adding a new `@media` rule, prefer reusing `640px` for "mobile" and
`768px`/`1024px`/`1440px` for progressively wider layout changes rather than
picking an arbitrary pixel value.

## 5. Accessibility minimums

- **Contrast ratios:** 4.5:1 for normal text, 3:1 for large text (≥18px
  regular / ≥14px bold), 7:1 for the `high-contrast` theme variant (WCAG
  AAA). All token pairs in §1 were chosen to satisfy this — do not override
  `--text` / `--bg` combinations with inline styles.
- **Focus order:** DOM order must match visual/reading order. Interactive
  elements inside overlays must trap focus while open and restore focus to
  the invoking control on close (see `role="dialog"` usages in
  `quick-actions.js`, `ootb-wizard.js`).
- **Target sizes:** minimum 44×44px (Apple HIG) / 48×48px (Material) for any
  tappable control on mobile breakpoints. `chump-nav`'s mobile cadence
  buttons are 44px tall for this reason — match that, don't shrink below it.
- **`prefers-reduced-motion`:** any animation/transition beyond a simple
  opacity or color fade must be gated behind
  `@media (prefers-reduced-motion: no-preference)` (precedent:
  `web/v2/ootb-wizard.js`) or check `window.matchMedia('(prefers-reduced-motion: reduce)')` before running JS-driven motion.
- **Landmarks:** one `role="main"` per page (`#main-content`), navigation
  regions use `role="tablist"` for cadence/sub-tab strips (see
  `.nav-cadences`, `.nav-subtabs` in `app.js`), and modal overlays use
  `role="dialog"` (or `role="alertdialog"` for confirmations that block
  further action) with `aria-modal="true"` and an `aria-label`.

## 6. Token discipline

New CSS in `web/**/*.{js,html,css}` is gated at pre-commit against raw color
literals, non-canonical token aliases, and mismatched `var()` fallbacks.
Full rule set, enforcement mechanism, and bypass trailer:
[`docs/process/CSS_TOKEN_DISCIPLINE.md`](../process/CSS_TOKEN_DISCIPLINE.md) (INFRA-1590).

## 7. When to add a new component vs. extend an existing one

Decision tree, checked in order:

1. **Does it fit inside an existing cadence view or footer/header slot
   without crowding it?** → extend the existing component. Adding a prop /
   slot is cheaper than a new custom element to maintain.
2. **Does it duplicate a metric or data display already shown elsewhere**
   (e.g. the same cost figure in both header and footer)? → don't add it;
   this is the duplicate-data-display anti-pattern (§8). Link to or reuse
   the existing display instead.
3. **Is it cross-cutting** (relevant across multiple cadences, e.g. an
   operator-attention queue or auth toast)? → new top-level component
   registered in `app.js`, mounted in the header or as a floating overlay
   per §3 — not nested inside a single view.
4. **Is it scoped to one cadence's data model and unlikely to be reused
   elsewhere?** → new `<chump-view-*>` (if it's a full view) or a plain
   nested component imported by that view (if it's a sub-widget) — not a
   new nav destination.

## 8. Anti-patterns

- **Duplicate data displays.** Don't show the same metric (cost, PR count,
  gap count) in both header and footer, or in two sibling views — pick one
  canonical location and link to it from elsewhere if context is needed.
- **Modal overlays without Escape.** Every `role="dialog"` /
  `role="alertdialog"` must close on `Escape` and clicking outside (unless
  it's a hard-blocking kill-switch modal, which must say so explicitly in
  its copy). A trapped operator with no way out is a support ticket.
- **Color literals outside tokens.** Any hex/`rgb()`/`rgba()`/`hsl()`
  literal outside `:root` / `[data-theme]` blocks is a token-discipline
  violation (§6) — it silently breaks theming when the operator switches
  themes.
- **Fixed-pixel widths in mobile media queries.** Inside a `@media
  (max-width: 640px)` block, prefer `flex: 1`, `%`, or `max-width` caps over
  a hardcoded `width: 320px`-style value — narrow devices vary enough (see
  §4's 375px floor) that a fixed width clips content on the smallest phones.

## Maintenance

Per the `project_doc_infrastructure` convention, the **tech-writer agent**
(`docs/agents/tech-writer.md`, hourly cadence) owns this document after
initial authorship: when a new `web/v2/*.js` file lands with a
`customElements.define()` call, tech-writer regenerates §2 via
`scripts/dev/gen-pwa-component-inventory.sh --write` and commits the diff.
Sections 1, 3–8 are structural/prose and are only touched when a human
PR changes the underlying tokens, breakpoints, or rules they describe.
